# C# 機台控制：相機取像與網球對位

[回到作品首頁](../README.md)

## 這支程式在產線上負責什麼？

C# 程式負責商標壓印前的網球對位。粗對位時，程式把姿態模型的預測換成馬達的旋轉與滾動指令。微調時，頂部相機量測縫線傾角和中心偏移，側面相機量測縫線高度。程式依這些偏差決定下一次轉球動作，直到位置、角度及球面條件符合要求，再通知下一站壓印。

## 接手後，哪些部分經過改寫？

機台使用兩套以 Python 訓練的模型。[姿態對位模型](alignment-training/README.md) 提供粗對位動作參數，[殘膠檢測模型](residue-training/README.md) 提供殘膠位置，供控制程式選擇可印刷的球面。

前代機台已具備自動轉球與雙相機微調功能。陳和欽接手後訓練新的姿態模型，讓模型一次估計粗對位所需的三個動作參數，將原來的兩步粗對位合併為一步。雙相機微調沿用並改良既有的幾何方法，C# 端則重寫了相機交付影像、啟動分析及接續機構動作的流程。

## 為什麼連取像與控制一起改？

調機時發現，微調程式有時仍依較早的影像計算縫線偏差。即使幾何計算正確，修正量也只適用於拍攝當時的姿態。粗對位縮短後，機台更快進入下一輪判斷，這個時序問題更常出現。

另一個改寫原因是背景工作之間的等待。前代由多個 `BackgroundWorker` 串接流程。取像工作先複製影像，分析工作等到取像進度回報才啟動，馬達完成動作後再由另一個回呼決定下一步。這些工作頻繁等待彼此回報，拖慢了整輪對位。

新版將頂部取像、側面取像與主控制拆成三個主要迴圈。控制程式等候馬達到位時，兩台相機仍可持續取像。何時啟動下一次分析，由主控制迴圈依機台狀態決定。微調需要的是球當下的偏差，因此控制端優先使用最新可用的影像，允許略過中間影格。

### 連續取像時，影像怎麼交接和釋放？

頂部相機與控制迴圈使用 C# 的 `lock` 保護只放一幀的緩衝區。新影像到達時，上一幀由誰釋放，取決於控制迴圈是否已經取走它。

| 新影像到達時     | 上一幀如何處理                                                |
| ---------- | ------------------------------------------------------ |
| 上一幀仍在緩衝區   | 相機端在鎖內釋放上一幀，再放入新影像。控制迴圈下次取像時就能讀到更新的球面姿態。        |
| 控制迴圈已取走上一幀 | 控制迴圈取走影像時已清空該位置，相機可以放入新幀。上一幀由控制端接手，機台狀態允許時送出分析，否則直接釋放。 |

操作畫面有獨立的顯示緩衝區。相機先更新控制用影像，如果顯示鎖正被占用，就略過這一幀的畫面更新。側面相機則重用二值化與遮罩運算的工作圖，只有影像尺寸改變時才重新配置。

## 實機對位改善了多少？

控制架構改寫前兩批的平均對位耗時為 **5.029、4.764 秒**，改寫後兩批為 **3.962、3.730 秒**。改寫後兩批的平均耗時均較短，也都有少數試次超過 10 秒。四批各自計時，批次差異的原因已無法追溯。[四批測試的試次與平均耗時](../docs/evaluation.md#控制架構改寫前後的四批測試)

前代與最終版另做整機比較，涵蓋姿態模型、轉球流程與程式調度等改良。[整機對位時間與逾時統計](../docs/evaluation.md)
